# 05. 피드백·재작성·로지텍 AI 검토·대기열

## 로컬 검토와 재작성

검토 입력은 동일 run의 Brief, Context Pack, 원고 revision, Claim map, 자산 binding이다. 기술적 검토와 편집 리뷰를 분리한다. 단어가 있다는 이유만으로 독자 질문 해결을 인정하거나 숫자가 다른 Fact에 존재한다는 이유로 근거 일치를 인정하지 않는다.

피드백 최소 항목: `feedback_id`, `draft_revision`, `location`, `category`, `severity`, `rule_ids`, `claim_ids`, `observation`, `requested_change`, `resolution_status`.

구매·도입 글의 편집 리뷰에는 [RULE-READER-STYLE의 독자 관점 검토](rules/reader-and-style.md#독자-관점의-편집-검토)를 적용한다. 고객의 구체적인 불편, 제품·기능의 기본 설명, 문제와 기능의 연결, 기본 구매·재사용 결론을 확인한다. 배선 설명이 구매 이유보다 앞서거나 문단에 서로 다른 문제가 섞이면 해당 문장을 인용하고 이동·축약·설명 보완 위치를 지정한다. 설치·설정 글에는 필요한 절차를 유지한다.

재작성 AI에는 문제 문장과 수정 요청, 보존할 Fact·지원 조건, 해당 독자 규칙 본문을 함께 전달한다. 수정 후 문제 제시부터 구성 결론까지 흐름과 앞뒤 문단 연결을 다시 검토한다. 자연스러운 말투나 작법 기법의 사용만으로 독자 질문이 해결됐다고 판정하지 않는다.

중심 결정의 개수는 독자에게 요구하는 구매·운영 선택으로 판단한다. 제품 정의·기능 비교·기본 사용 모습·조건부 부속이 하나의 구매 판단을 돕는다면 이를 분리 요구의 근거로 삼지 않는다. 필요한 기능의 개요·비교표·공식 동작 자료가 빠졌는지와 내부 검토 문장이 본문으로 출력됐는지도 확인한다.

문단을 이동·수정한 뒤에는 이미지의 배치 앵커와 해당 문단의 의미를 다시 맞춘다. 제품 실물·공식 동작 자료·생성 상황 이미지의 역할을 구분하고, 설명 문단별 자산 누락·불필요한 중복·이미지 내 한글·암시된 제품 주장을 검토한다. GIF는 확장자만 보지 않고 실제 프레임과 재생 여부를 확인한다. 검토 전 생성 성공을 승인으로 처리하지 않는다.

AI는 수정본과 피드백별 조치 기록을 반환한다. 단순 어투 수정도 새 revision으로 저장한다. 새 제품·기능·수치·이미지 문구가 들어오면 Fact/주의사항/이미지 검토를 다시 수행한다. 재시도 횟수는 run 설정으로 관리하며 소진 시 unresolved를 남긴다. 실패한 마지막 원고를 승인본으로 바꾸지 않는다.

## 로지텍 AI에 검토 요청

재작성된 후보 원고의 정확한 revision/hash를 고정하고 다음을 전달한다.

```text
목적: 이 원고의 제조사 기술 주장 검토
대상: 제품/기능/플랫폼/버전 범위, 원고 revision/hash
자료: 원고 전문, 기술 Claim 목록, 연결된 Fact와 source locator
요청: Claim별 confirmed / contradicted / insufficient_evidence / out_of_scope
응답: claim_id, 판정, 이유, 공식 출처·문서 위치, 가능한 정정 제안
금지: 파트너사 경험·실적·서비스 정책을 제조사 공식 확인으로 간주하기
```

자연어 응답만 받을 수 있으면 원문을 보존하고 구조화 변환 결과를 검증한다. 구조화 실패·무응답·시간초과는 ERROR/UNKNOWN이며 PASS를 생성하지 않는다. AI 답변의 출처를 확인할 수 없으면 ‘AI 의견’으로 남기고 공식 Fact 확정으로 취급하지 않는다. 제목·표·이미지 문구도 검토 대상에 포함한다.

## 틀린 내용 → 지식 업데이트 대기열

`knowledge_update_queue`는 확정 수정 명령이 아니라 불일치 및 변경 제안 대기열이다. 다음 분류를 함께 남긴다.

- `DRAFT_ERROR`: 기존 공식 근거와 지식이 맞고 원고가 틀림. 원고 재작성 필요, 지식 변경 불필요.
- `KNOWLEDGE_CHANGE_CANDIDATE`: 기존 지식이 오래됐거나 틀렸을 가능성. 최신 공식 문서 확인과 큐레이터 판단 필요.
- `SOURCE_CONFLICT`: 문서·버전·조건이 달라 충돌. 어떤 조건에서 무엇이 맞는지 확인 필요.

각 항목에 content/run/revision, Claim/Fact ID, 원문 주장, 기존 값, 제안값, AI 응답, 공식 source locator, 영향 콘텐츠, 상태, 담당자를 기록한다. 큐레이터가 근거를 확인하고 승인한 뒤 새 Fact revision을 만든다. 기존 Fact를 덮어써 이미 승인된 원고의 검증 근거를 바꾸지 않는다.

## 판단 불가 → 관리자 검토 대기열

예: 실제 쇼룸 테스트 여부, 자체 사진 사용 권한, 기업 상담·대여 조건, 브랜드 표현 정책, 공식 출처 간 충돌을 추가 조사할 담당자 지정.

관리자 항목에는 `item_id`, `claim_id/asset_id`, `draft_revision`, `question`, `why_ai_cannot_decide`, `evidence_needed`, `allowed_decisions`, `blocking`, `assignee`, `status`, `reviewer`, `reviewed_at`, `decision_note`를 둔다. 답변 선택지는 승인/수정 요청/삭제/추가 근거 요청 등 항목에 맞춰 제시하며 승인을 미리 추천하지 않는다.

기술 근거가 부족한 주장은 관리자가 ‘문구가 좋다’고 승인해도 Fact 검증을 통과하지 못한다. 관리자 판단으로 유지할 수 있는 업무 정책·경험 주장도 근거 기록과 책임자를 남긴다.

## 재검토와 종료

지식 수정·관리자 피드백·이미지 수정 후 새 원고 revision이 생기면 관련 검토를 다시 수행한다. 변경되지 않은 검토의 재사용은 검사 대상 hash가 동일할 때만 가능하다. 같은 검토를 재시도해도 `(run_id, revision, item_id)`로 중복 큐 항목을 만들지 않는다.

공식 검토에서 ‘확인됨’과 ‘틀림’을 같은 Claim에 동시에 넣지 않는다. 판단 불가를 긍정으로 바꾸지 않는다. 두 대기열에 관련 항목을 만들 수는 있지만 상호 참조와 단일 해결 이력을 유지한다.
