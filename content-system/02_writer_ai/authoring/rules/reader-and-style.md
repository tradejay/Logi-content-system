# RULE-READER-STYLE — 질문 해결과 문체

Version: 1.2.0

이번 글의 독자 질문에 답하는 내용부터 쓰고 필요한 기술 용어를 일상어에 연결한다. 질문 속 단어를 반복하는 것만으로 답변했다고 판단하지 않는다. 관련 없는 스펙은 생략하되 선택에 필요한 제한 조건은 남긴다.

초반에는 문제와 답, 중반에는 선택된 설명 모듈, 마감에는 판단과 다음 행동을 연결한다. 내부 Fact ID나 기계적 채점 라벨을 본문에 노출하지 않는다. 강한 마케팅 표현을 근거 없는 다른 성능 표현으로 바꾸지 않는다.

## 구매·도입 글의 작성 지시

아래 지시를 해당 글의 독자 질문, 선택한 Fact와 적용 조건, 기본 구성 계획과 함께 기획·집필·재작성 AI에 전달한다. 규칙 ID만 전달하고 본문을 생략하지 않는다. 설치·설정 목적의 글에는 그 목적에 필요한 절차를 유지한다.

> 독자는 회의실의 불편을 해결하려는 고객이다. 먼저 고객이 겪는 구체적인 장면과 불편을 설명하고, 필요한 변화에 답하는 기능을 쉬운 말로 소개한다. 제품은 무엇인지, 기능은 무엇을 하는지, 이번 구성에서 왜 필요한지 연결한다. 본문 순서는 고객 장면 → 불편 → 필요한 변화 → 기능과 근거 → 기본 구성과 사용 모습 → 적용 조건 → 구매·재사용 결론을 기준으로 조정한다. 배선도의 순서를 글의 순서로 복사하지 않는다. 포트와 케이블의 세부 절차는 독자의 구매 판단이나 사용 이해에 필요할 때만 포함한다. 확인된 사실은 적용 범위를 포함해 직접 설명하고, 근거가 부족한 주장은 범위를 좁히거나 제외한다. 독자에게 사실 확인을 떠넘기는 문장으로 마무리하지 않는다. 한 글의 중심 결정과 공통 전제를 유지하고, 사례·효과·호환성을 만들어내지 않는다.

### 작성·재작성 절차

1. 기획에서 독자, 불편, 원하는 변화, 기존 장비·운영 방식, 중심 결정과 구성 결론을 먼저 정한다. 문제가 설정·배치 조정으로 해결되면 구매를 강요하지 않는다.
2. 각 섹션에 “어떤 독자 질문에 답하는가”를 붙여 계획한다. 답할 질문이 없는 스펙·부속 설명은 생략하거나 별도 글로 보낸다.
3. 제품·기능을 처음 소개할 때 기본 정의와 역할을 설명한다. 기능명만 적거나 공식 수치만 나열한 문단을 문제와 연결해 고친다.
4. 기능의 동작과 고객에게 주는 의미를 구분한다. 사실이 “발언자 중심 화면 제공”이면 이를 설명하되 “회의 집중도 향상 보장”처럼 근거 없는 효과로 확대하지 않는다.
5. 구성은 구매할 것, 재사용할 것, 각 장비의 역할과 회의를 사용하는 모습을 설명한다. 포트 종류·개수·배선·버전이 판단에 중요하면 정확한 조건을 남긴다. 단순화하면서 운영 방식이나 제약을 바꾸지 않는다.
6. 문단을 재배치할 때 정의가 기능 설명보다 앞서는지, 같은 문제에 답하는 문장끼리 묶였는지 확인한다. 예를 들어 플랫폼 버전과 회의실 음향은 각각 지원 조건과 수음 문제로 구분하고, 관계가 설명되지 않으면 한 문단에 묶지 않는다.
7. 결론에서 초반 불편을 회수하고 기본 구성의 추천 이유와 적용 조건을 짧게 정리한다. 추가 부속은 남는 문제가 있을 때만 제시한다. 결론에서 처음 등장하는 부속도 제품명만 던지지 않고 보완할 문제·역할·근거를 짧게 설명하며, 별도의 구매 분기를 늘리지 않는다.
8. 중심 결정이 제품 구매라면 제품 정의, 기능 비교, 기본 사용 모습, 조건부 부속 설명은 이를 뒷받침하는 내용이다. 기능을 설명했다는 이유만으로 중심 결정이 여러 개라고 판정하지 않는다. 독자가 독립된 운영 구성·제품 대안을 선택해야 하는 분기가 실제로 늘어났는지 확인한다.
9. “검토 항목으로 남깁니다”, “근거로 삼지 않습니다” 같은 내부 지시를 독자용 본문에 복사하지 않는다. 확인된 사실은 조건과 함께 직접 전달하고 미확인 주장은 조사 항목으로 분리한다. 표현을 우회해 미확인 사실을 암시하거나 중요한 제약을 숨기지 않는다.
10. 구매 이유에 필요한 기능 차이는 기본 정의와 같은 기준의 비교로 설명한다. 표·공식 동작 GIF·참고 링크가 이해를 돕는 경우 해당 위치에 계획하며, 중심 결정이 하나라는 이유로 근거 자료를 생략하지 않는다.

### 편집 방향 예시

아래 문장은 편집 패턴의 예이며 제품 지원 사실이나 실제 고객 사례의 근거로 사용하지 않는다.

- 연결부터 시작한 문장: “노트북과 장비를 USB로 연결하고 디스플레이를 HDMI로 연결합니다.”
- 문제부터 시작한 문장: “회의실 전체가 화면에 잡혀도, 원격 참석자에게는 누가 말하는지 잘 보이지 않을 수 있습니다. 이번 글에서는 발언자를 중심으로 보여주는 기능과 기존 TV·노트북을 활용하는 구성을 살펴봅니다.”

전자는 연결 방법을 찾는 독자에게 적합하다. 후자는 구매·도입 글의 도입에 적합하며, 실제 제품 동작과 구성은 제공된 Fact로 뒷받침해야 한다.

## 독자 관점의 편집 검토

- 도입에 구체적인 불편이 있는가? “좋은 회의 환경” 같은 추상적인 표현만으로 문제 설명을 끝내지 않았는가?
- 제품을 모르는 독자가 제품·기능의 기본 역할을 이해할 수 있는가?
- 각 섹션의 기능·스펙이 독자의 문제 또는 구성 판단과 연결되는가?
- 포트 설명을 읽기 전에도 무엇을 왜 도입하는지 이해할 수 있는가? 설치 글이라면 필요한 작업 순서가 명확한가?
- 한 문단의 문장들이 같은 질문에 답하는가? 지원 조건, 음향, 화면 구도 등 다른 문제들이 설명 없이 섞이지 않았는가?
- 쉽게 풀어쓰면서 중요한 지원 조건을 지우거나 근거 없는 효능을 추가하지 않았는가?
- 결론에 기본 구매·재사용 구성과 적용 조건이 남고, 해결과 무관한 선택지가 늘어나지 않았는가?
- 기능 정의·비교가 구매 이유를 뒷받침하는가? 설명을 별도 결정으로 잘못 세어 필요한 내용을 삭제하지 않았는가?
- 내부 검토 지시가 본문에 노출되거나 사실 확인을 독자에게 떠넘기지 않았는가?
- 실제 제품 외형과 기능 동작을 확인할 자료, 설명 문단에 대응하는 이미지가 계획되어 있는가? 생성 이미지가 공식 근거를 대신하지 않았는가?

검토 출력: 질문별 답변 위치와 실질적 해결 여부, 문제 문장의 인용·위치, 독자에게 생기는 혼란, 구체적인 수정 요청, 보존할 Fact·조건. “고객 중심으로 고칠 것”이라는 요청만 남기지 않고 무엇을 앞세우고 무엇을 옮길지 적는다. 수정 후 해당 문단과 앞뒤 연결을 다시 읽고, 추가·변경된 사실은 팩트 검토로 돌린다. 단어 출현 횟수만으로 이 기준을 통과했다고 판정하지 않는다.
