# 03. AI에 전달할 작성 방식 — 초반·중반·마감

## 기획 AI에 주는 작업

Brief의 검색 의도, 질문, 추출한 Fact를 읽고 질문 해결 순서를 계획한다. 기존 플레이북은 선택 가능한 편집 패턴이며 예문에 들어 있는 제품 수치나 성능 설명은 근거가 아니다. Primary 1개와 필요한 보조 모드만 선택하고 선택 이유를 기록한다.

Strategy는 `article_goal`, `reader.questions`, `primary_playbook`, `secondary_playbooks`, `must_cover`, `can_omit`, `avoid`, `technical_depth.overall`, `opening`, `body`, `closing`, `asset_needs`를 포함한다. 질문과 Fact ID를 연결하고, 승인된 사용자 기획을 일반 질문 템플릿으로 덮어쓰지 않는다.

## 고객이 읽는 글 — 자료의 구조를 독자의 문제로 바꾸기

구매·도입 목적의 글은 회의실 문제를 해결하려는 고객을 독자로 잡는다. 배선도와 스펙표는 구성의 정확성을 확인하는 근거다. 자료의 노드·포트 순서를 그대로 본문 순서로 옮기면 설치 절차가 앞서고 구매 이유가 사라지므로, 먼저 고객의 불편과 원하는 변화를 정한다. 설치·설정 자체가 검색 의도인 글은 그 목적에 맞는 절차를 제공한다.

기획 AI는 **고객이 겪는 장면 / 구체적인 불편 / 원하는 변화 / 이미 가진 장비·운영 방식 / 기능이 문제에 답하는 이유 / 기본 구성 결론**을 기존 Strategy의 독자 질문·본문 계획·필수 내용에 기록한다. 새로운 필수 API 필드를 추가한다는 뜻은 아니다. 실재 사례가 없으면 가정한 장면으로 쓰고 실제 고객 경험으로 꾸미지 않는다.

집필·재작성 AI에는 [고객 중심 작성 지시와 검토 기준](rules/reader-and-style.md)을 전달한다. 제품 설명은 “무엇인가 → 어떤 불편에 필요한가 → 이번 구성에서 맡는 역할”로 연결한다. 케이블·포트·버전은 구매 판단이나 사용 제약에 필요한 만큼 남긴다. 다이어그램으로 확인한 내부 컴퓨팅과 회의 앱 실행 위치 등은 구성 오류를 막는 근거로 활용하되, 이번 글의 전제와 다른 운영 방식을 모두 소개하지 않는다.

## 글의 범위와 선택지 — 한 글에서 한 가지 결정을 돕기

추가일: 2026-10-02 / 사용자 요청 반영.

먼저 **고객 문제 → 이미 가진 장비·운영 방식 → 이번 글의 구성 결론**을 한 문장으로 정한다. 구성·설치 글은 하나의 기본 구성을 설명하고, 비교 글은 같은 결정 질문에 답하는 비교군을 다룬다. 제품 구매를 중심 결정으로 삼았다면 제품 정의, 기능의 차이, 기본 사용 방식, 조건부 부속은 그 결정을 뒷받침하는 설명으로 함께 다룰 수 있다. 이 설명들을 각각 별도의 구매 결정으로 세어 글을 강제로 분리하지 않는다. 독자가 서로 다른 운영 구성이나 제품 대안을 모두 선택해야 할 정도로 분기가 늘어날 때 범위를 좁힌다.

| 결정 질문 | 같은 선상의 비교군 예시 | 구분할 것 |
|---|---|---|
| 메인 장비를 무엇으로 할까? | Rally Bar ↔ Rally Bar Mini | 제품 선택 |
| 어디에서 회의 앱을 실행할까? | 개인 노트북(BYOD) ↔ 장비 내부 컴퓨팅(CollabOS 기반 실행) | 회의 실행 방식 |
| 참석자를 어떤 화면으로 보여줄까? | 전체 참석자(Group View) ↔ 발언자 중심(Speaker View) | 화면 구도 |
| 어떤 기능을 추가할까? | 필요한 역할별 부속을 개별 검토 | 기본 구성의 확장; 서로 대체하는 비교군이 아님 |

Sight는 촬영 시점, Mic Pod는 수음 확장, Tap IP는 회의 조작 등 역할이 다르므로 같은 구매 비교표의 대안으로 나열하지 않는다. 이 예시는 기획 분류이며 기능·호환성·필수 구성의 근거가 아니다. 실제 적용은 선택한 제품·모드·플랫폼의 Fact와 배선 자료로 확인한다.

### 기획·집필 방법

- 한 글의 중심 결정은 하나로 좁힌다. 설치 글에서는 제품·운영 방식을 전제로 고정할 수 있고, 비교 글에서는 비교할 축 하나를 중심으로 잡는다.
- 전제로 고정한 항목은 도입에서 짧게 밝힌다. 구매·도입 글의 예: “기존 TV와 개인 노트북을 사용하는 회의실에서, 발언자의 얼굴을 더 잘 보여줄 방법을 살펴봅니다.”
- 선택지는 **기본 구성 / 조건부 추가 / 다른 글에서 다룰 대안**으로 정리한다. 같은 기준으로 비교할 수 없는 장비를 동급 대안으로 취급하지 않는다.
- 구매·도입 글은 **고객 장면과 불편 → 필요한 변화 → 기능의 쉬운 설명과 근거 → 기본 구성과 사용 모습 → 적용 조건 → 구매·재사용 결론**으로 전개한다. 설치 글은 연결 순서와 동작 확인을 중심으로 조정한다.
- 추가 장비는 “어떤 문제가 남을 때 필요한가”와 함께 짧게 설명한다. 해당 부속의 실제 사진과 등록된 제품 소개 URL을 함께 계획한다. 추가 설명이 별도의 구성·설정 절차를 요구하면 상세 절차를 독립 콘티로 분리하되, 구매 판단에 필요한 짧은 설명까지 삭제하지 않는다.
- 마무리는 기본 구매·재사용·연결 구성을 회수한다. 설정·배치 조정만으로 해결되는 문제는 불필요한 구매로 연결하지 않는다. 미확정 지원 조건은 숨기지 않는다.
- 관련 글 링크는 실제 등록된 URL이 있을 때만 연결한다. 아직 작성하지 않은 글은 내부 기획 목록에 남긴다.

### 여러 글로 나누는 콘티 예시

| 글 | 이번 글에서 답할 결정 | 본문에서 고정하거나 분리할 항목 |
|---|---|---|
| 기존 TV·노트북으로 화자 추적 구성하기 | 기본 구성과 연결·사용 방법 | BYOD와 메인 장비를 전제로 고정 |
| Rally Bar와 Mini 중 무엇을 선택할까? | 동일한 사용 요구에서 제품 차이 비교 | 운영 방식을 공통 전제로 고정 |
| 노트북 없이 회의실에서 회의 시작하기 | 내부 컴퓨팅 기반 구성과 운영 | BYOD 상세 설명은 별도 글 |
| 전체 참석자 화면과 발언자 화면의 차이 | 화면 구도 선택 | 장비·운영 환경은 공통 전제 |
| 테이블 중앙 촬영 또는 끝자리 음성 보완하기 | 각각 촬영 시점 / 수음 확장의 필요성 | 목적이 다른 두 주제는 각각 독립 글로 기획 |

글별 기획에는 **독자 문제, 공통 전제, 중심 결정·비교군, 기본 구성 결론, 조건부 추가, 이번 글에서 제외할 대안, 필요한 근거**를 기록한다. 구매·도입 원고에서는 독자가 “내 불편에 왜 이 기능이 필요하고, 무엇을 구매·재사용해 어떻게 쓰는가”를 설명할 수 있는지 확인한다. 설치 글은 연결과 동작 확인, 비교·개념 글은 그 목적에 맞는 선택 기준이나 다음 판단이 남는지 확인한다.

## 초반 — 인사·주제 예고·문의 배너 후 문제와 답

[오우션 공통 규칙](rules/oceantech-brand-and-links.md)에 따라 제목 다음에 오우션테크놀러지 총판 첫인사, B2B 견적 및 데모 제품 지원 안내, 독자 고민 공감 및 주제 제시를 자연스러운 대화체 화법으로 풀어 배치한다. (예시 문구를 기계적으로 복제하지 않는다.) 이어서 지정된 문의 문구와 클릭 가능한 배너 이미지(`{{asset:oceantech-inquiry-opening}}`)를 넣고 아래 도입 설명으로 연결한다.

- 검색자가 처한 구체적인 상황을 일상어로 짚는다. 모든 글을 동일한 회의실 고충 문장으로 시작하지 않는다.
- 첫 부분에서 이번 글이 답할 질문과 조건부 핵심 답을 준다. 답을 낼 근거가 없으면 확정 결론을 약속하지 않는다.
- 기능명은 필요할 때 일상어에 연결한다. 브랜드/제품명이 검색 의도에 필수라면 초반에 자연스럽게 언급할 수 있다.
- 제품 나열, 추상적인 산업 동향, 검증되지 않은 성공 경험으로 도입을 채우지 않는다.
- 대표 이미지가 문제 이해에 도움이 되면 사용한다. 모든 글에 회의실 실사 이미지를 강제로 넣지 않는다.

## 중반 — 질문 → 설명 → 근거 → 적용 조건

한 덩어리는 한 질문을 해결한다. 설명에는 필요한 Fact만 쓰고, 독자가 어떤 판단을 할 수 있는지 연결한다. 다음 모듈을 필요에 따라 선택한다.

| 모듈 | 선택 조건 | 반드시 포함할 것 |
|---|---|---|
| 원리 설명 | 왜/어떻게 작동하는가가 핵심 | 공식 확인된 입력·동작·결과·확인 범위 |
| 스펙 해석 | 수치가 구매/설정 판단에 필요 | 속성·단위·조건 및 독자에게 주는 의미 |
| 비교 | 둘 이상의 선택지를 비교 | 동일 기준, 확인된 차이, 적합 조건과 한계 |
| 설정 방법 | 독자가 직접 작업해야 함 | 제품/버전, 공식 메뉴·절차, 확인 방법 |
| 구성/배선 | 연결 관계가 핵심 | 확인된 구성요소·호환성·제약 및 필요한 도식 |
| 실증/사례 | 실제 기록이 제공됨 | 테스트 주체·환경·일자·측정/관찰 기록 |
| 한계/주의 | 잘못 적용할 가능성 있음 | 해당 Fact와 연결된 주의사항 및 검증된 대안 |

섹션 번호에 역할을 고정하지 않는다. 모든 글에 스펙표, 센서 융합, 모드 비교, 배선도를 요구하지 않는다. 근거 없는 고객사 사례를 ‘쇼룸 실증’으로 바꿔 쓰지 않는다. 설명용 가상 상황은 가정임을 명시하고 관찰 사실처럼 쓰지 않는다.

### 기본 설명과 기능 비교를 빠뜨리지 않기

제품을 처음 접하는 독자가 이해할 수 있도록 “어떤 장비인가 / 무엇을 하는 기능인가 / 고객의 불편과 어떤 관계가 있는가”를 필요한 위치에서 설명한다. 고객 문제보다 앞에 모든 용어 정의를 모아 놓는 고정 개요 장은 요구하지 않는다. 기능을 비교하기 전에 각 기능의 기본 의미가 소개되어 있으면 된다.

구매 이유가 두 기능의 차이에 기대는 경우에는 명칭만 언급하지 않고 동일 기준의 차이를 설명한다. 비교표가 이해를 돕는다면 동작, 화면 구성, 사용 장면, 적용 조건 중 근거가 있는 항목으로 표를 만든다. 실제 동작을 보여주는 공식 GIF·영상과 공식 설명 링크가 있으면 해당 설명 위치의 자산으로 계획한다. 예를 들어 Group View와 Speaker View의 설명은 Rally Bar 구매 이유를 뒷받침할 수 있으며, 이를 포함했다는 이유만으로 별도 선택 글로 분리하지 않는다. 제품별 사실과 URL은 현재 자료에서 확인하며 이 예문을 근거로 사용하지 않는다.

### 내부 판단과 독자에게 전달할 설명 구분

“검토할 항목으로 남깁니다”, “향상의 근거로 삼지 않습니다”처럼 작성자에게 주는 검토 지시를 본문으로 출력하지 않는다. 확인된 기능과 조건은 쉬운 말로 직접 설명한다. 확인되지 않은 범위는 조사·관리자 항목에 기록하고, 본문은 확인된 범위로 좁힌다. 독자의 실제 선택에 중요한 미확정 조건은 숨기거나 표현만 바꿔 확정 사실처럼 만들지 않는다. 추가 장비는 내부 금지 규정 대신 해당 장비가 실제로 보완하는 문제와 역할을 설명한다.

이미지는 설명을 읽다가 ‘어떻게 생겼지/어떻게 다르지/어디에 연결하지’를 확인하는 지점에 둔다. 이미지가 있다는 이유로 관련 없는 문단을 늘리지 않는다.

제품을 설명하는 문단 바로 다음에는 Blog Manager 원본에서 해당 제품 ID로 확인한 소개 글 링크를 넣는다. 제품이 여러 개면 각각 연결하고 같은 제품의 불필요한 반복은 피한다. 원본 경로·필드·누락 처리는 [제품 링크 규칙](rules/oceantech-brand-and-links.md)을 따른다.

## 마감 — 판단과 다음 행동

- 초반 질문에 대한 답을 짧게 회수한다.
- 독자가 자기 환경에서 판단할 기준 또는 다음 행동을 제시한다. 기본 결론을 바꾸는 새 스펙·새 기능을 끝에서 갑자기 추가하지 않는다. 남는 문제의 조건부 부속은 역할과 근거를 짧게 설명하고 실제 사진·소개 링크를 연결할 수 있다.
- 제품 소개 글 링크는 해당 설명 문단에 제품별로 배치한다. 전체 글 1개 제한은 적용하지 않는다. 미확인 링크는 관리자 보완 항목으로 남긴다.
- 마지막 인사말 뒤에 도입부와 동일한 오우션 문의 문구·클릭 가능한 배너를 반드시 넣는다. 구체적인 인사말은 [공통 규칙](rules/oceantech-brand-and-links.md)을 따른다. 무료 제공, 납품 실적, 상담 범위를 임의로 약속하지 않는다.
- CTA 이미지/배너 HTML은 승인된 템플릿과 Asset binding으로 렌더링한다. 모델에게 고정 URL·배너 HTML을 재생성하게 하지 않는다.

## 블로그 문체와 출력

기본은 친절한 경어체와 짧은 문단이다. 한 문단 2~3문장을 편집 목표로 삼되 내용상 필요한 예외를 허용한다. 2,000~3,000자와 H2 4~5개는 시작 목표로만 사용하며 검색 의도와 근거에 따라 Strategy에서 조정한다. 숫자를 맞추기 위한 군더더기나 중요 제약 삭제를 금지한다.

전문용어는 설명과 함께 도입하고, 무조건적 찬사·정확도·무오작동·업계 보급률 주장은 근거 없으면 쓰지 않는다. ‘완벽한’을 ‘오차 없는’으로 바꾸는 것도 근거 없는 성능 주장이다. 정수값의 불필요한 `.0`은 정리할 수 있으나 실제 소수 정밀도와 단위를 훼손하지 않는다.

원고 출력은 `markdown` + `claims` + `changes` + `used_asset_need_ids` + `unresolved_items`다. 본문에는 내부 채점 라벨/Claim ID를 노출하지 않는다. 출력 메타데이터의 날짜는 작성일이며 발행일은 실제 게시 후 별도로 등록한다.

집필 응답의 used_asset_need_ids는 본문 이미지 자리 표시자의 Need ID 전체를 중복 없이 나열한다. unresolved_items는 kind(asset/link/evidence/other), detail, need_id(asset일 때 필수)를 기록한다. 이미지 제작·검토 대기는 후속 자산 단계로 진행할 수 있지만 기술 근거·링크 등 원고의 미해결 항목은 보완·제외 후 재검토한다. changes는 수정 이력이다. 파이프라인은 본문과 Need ID 목록을 대조하고, 이미지 승인 상태는 실제 binding과 승인 기록에서 확인한다.
