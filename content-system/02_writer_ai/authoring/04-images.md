# 04. 이미지 계획·확보·생성·URL·삽입

## 초안에서 자리를 계획하고, 본문 확정 후 확보·제작·승인한다

사용자 지정 [오우션 문의 배너](rules/oceantech-brand-and-links.md)는 도입부와 마지막 인사 뒤의 필수 공통 자산이다. 동일한 배너 이미지와 문의 링크를 두 위치에 배치하고 중복 제거하지 않는다. 제품 설명용 이미지와 별도로 계획하며, 지정 HTML·URL을 가이드에서 읽어 바인딩한다.

초안 작성 시 문단별 시각적 질문을 정하고 `{{asset:NEED-ID}}`로 이미지 자리를 표시한다. Need ID는 이미지 요구사항의 ID이며 실제 파일이나 승인된 Asset ID가 아니다. 미확보·미승인 이미지도 초안의 자리 표시자로 계획할 수 있다. 본문 편집 확정 후 공식 자료를 연결하거나 생성 이미지를 제작하고, 내용·출처·권한·배치·URL을 검토한다. 최종 출력은 Need ID에 연결된 승인된 Asset ID/revision만 사용한다. 본문 변경 시 해당 이미지와 배치도 재검토한다.

각 이미지 요구는 `need_id`, `question_id`, `section_key`, `placement_anchor`, `purpose`, `asset_type`, `entity_ids`, `fact_ids`, `required`, `fallback`을 가진다. section_key는 이번 글의 의미 있는 키이며 SEC 번호에 제품을 연결하지 않는다.

자료 선택 순서:

1. 현재 질문과 제품·기능·버전이 맞는 승인된 공식 이미지/GIF/매뉴얼 화면 확인.
2. 사용 권한과 실증 기록이 확인된 자체 자료 확인.
3. 적합한 자산이 없으면 문단의 시각적 질문에 따라 생성 요청을 고른다. 고객 상황·환경은 간단한 회의 모습 사진, 개념·차이·핵심 정리는 문단 내용에 맞는 한글 설명 카드로 계획한다. 공식 자료 부재만으로 모든 문단에 회의 사진을 자동 배치하지 않는다.
4. 공식 UI, 실제 제품 구조, 테스트 결과의 증거가 필요하면 생성으로 대체하지 않고 자료 요청.

본문의 설명 문단별로 시각적 질문과 대응 자산을 점검한다. 기존 사진·GIF로 답할 수 있는 문단은 그 자산을 연결하고, 대응 자산이 없는 설명 문단은 관련 상황 이미지나 설명 카드를 생성하도록 계획한다. 단순 인사·문의 문구, 앞 문단과 같은 시각적 질문을 반복하는 문단은 예외로 기록할 수 있다. 문단마다 기계적으로 새 파일을 생성하거나 전체 글 이미지 수를 코드로 고정하지 않는다. 한 섹션 안에서도 제품 외형, 기능 동작, 고객 문제처럼 서로 다른 역할의 자료를 함께 배치할 수 있다.

## 생성 요청 및 AI 생성 이미지(나노바나나 파이프라인) 가이드

생성 AI(Google Gemini / 나노바나나 파이프라인 `nano_banana_pipeline.py`)에는 시각 목적, 포함할 사실과 출처 ID, 표시할 문구, 허용 표현, 금지 요소, 스타일/화면비, 배치 맥락을 전달한다. 제품 성능·거리·포트 구성·화면 메뉴를 이미지 모델에게 추정하게 하지 않는다.

### 1. 허용 및 권장 생성 대상 (회의실 전경, 상황, 아키텍처)
- **회의실 전경 및 비즈니스 상황 실사 (Corporate Photo)**:
  - 배선 없는 스마트 회의실 전경(`AST-PHOTO-ROOM-SCENE-001`), 활발한 팀 회의 토론 모습(`AST-PHOTO-TEAM-DISCUSS-001`), 프레젠테이션 진행 모습(`AST-PHOTO-PRESENTER-001`) 등.
  - **용도**: 도입부 독자 공감 형성, 문제 제기 파트의 현장감 연출, 마무리 전 체크리스트/도입 권유 파트의 분위기 환기.
  - **주의**: 하드웨어 제품 자체(로지텍 랠리바 렌즈 모양, 후면 포트, Tap 패널 규격 등)를 AI로 왜곡하여 렌더링하지 않으며, 제품 실물은 반드시 공식 자산을 사용한다. 회의실 공간 분위기와 사용자 환경을 표현할 때 활용한다.
- **고충 및 문제 상황 일러스트 (Pain Situation)**:
  - 회의실 안에서는 서로의 얼굴을 보지만 원격 화면에서는 얼굴이 작게 보이는 상황, 발언자를 구분하기 어려울 수 있는 상황 등 문제 제기용 2.5D 일러스트. 일반적 가상 상황으로 표현하며 특정 장비의 고장·오작동·성능 열위를 암시하지 않는다.
- **개념 설명형 프레젠테이션 인포그래픽 (Concept Presentation)**:
  - 문단의 핵심 문제, 상황 차이, 구성 요소의 역할을 설명하는 슬라이드. 숫자·기술 원리·기능 비교가 들어가면 각각 연결된 Fact와 조건이 있어야 한다. 예문의 화각·추적 방식 등을 제품 근거로 복제하지 않는다.

### 문단 내용에 맞는 생성 방식 선택

- 분위기나 사용 환경을 전달할 때는 회의, 유리벽 회의실, 노트북 사용, 발표 등 본문과 가볍게 연결되는 상황 사진을 사용한다. 제품의 외형·연결·화면 동작·지원 기능을 모델이 만들어내게 하지 않는다.
- 문제를 빠르게 이해시키려면 PPT 페이지처럼 **짧은 한글 제목 + 상황 그림 + 핵심 불편 목록**으로 구성한 설명 카드를 선택한다. 장면 비교가 목적이면 회의실 내부와 원격 화면을 나란히 보여줄 수 있다. 모든 이미지에 목록이나 O/X를 강제하지 않는다.
- 목록은 해당 문단이 말하는 문제만 담는다. 예: 작은 얼굴로 인해 발언자·표정·입 움직임을 구분하기 어려울 수 있다는 가상 상황. 해결 효과·정확도·제품 간 우열을 추가하지 않는다. 가능한 것/불가능한 것 표시는 공식 지원 조건이 확인된 경우에만 사용한다.
- 생성 전 문단 원문, 전달할 핵심, 정확한 한글 문구, 표현하면 안 되는 제품 주장, 배치 위치를 함께 전달한다. 생성 후 문단과의 관련성, 한글 오탈자, 암시된 기능·성능을 시각적으로 확인하고 수정 또는 재생성한다.
- 실제 제품 소개는 공식 제품 사진, 실제 기능 설명은 공식 GIF·영상, 고객 문제와 환경은 생성 이미지로 역할을 구분한다. 생성 이미지가 있다는 이유로 Rally Bar 등 메인 제품 사진이나 기능 동작 자료를 생략하지 않는다. 조건부 부속도 설명한 위치에 실제 사진과 등록된 소개 링크를 연결한다.

### 2. 생성 스타일 및 렌더링 절대 원칙
- **100% 네이티브 한글 직접 생성 원칙**:
  - 인포그래픽이나 슬라이드에 텍스트가 포함될 경우, 반드시 프롬프트 단계부터 정확한 한국어 레이아웃을 지정하여 생성한다.
  - **영문 생성 후 불투명한 한글 박스를 외부에 덧씌우는 조잡한 패치(Overlay Box) 방식은 엄격히 금지**하며, 글자 깨짐이나 오탈자 발생 시 재생성한다.
- **2.5D 모던 비즈니스 스타일**: 개념 슬라이드 및 고충 일러스트는 산만하지 않은 단정한 2.5D 비즈니스 벡터/일러스트 스타일을 기본으로 한다.
- **역할별 배치 및 과밀 방지**:
  - 섹션 단위의 1장 제한보다 설명 문단의 시각적 질문을 기준으로 배치한다. 공식 사진과 GIF, 생성 설명 카드가 서로 다른 질문에 답하면 같은 섹션에 함께 사용할 수 있다.
  - 같은 역할의 사진을 연속으로 반복하거나 본문과 무관한 장면으로 자리를 채우지 않는다. 문단별 연결과 중복 여부를 자산 계획에 기록한다.
- **진실성 유지 (RULE-ASSET-TRUTH)**:
  - 이미지 안 문구도 본문과 동일한 Claim이다. 레이아웃이나 라벨이 사실을 왜곡하지 않아야 한다.
  - AI 생성 이미지가 아무리 정교하더라도 실제 고객사 설치 사례나 공인 시험 성적의 증거 사진인 것처럼 소개하지 않는다.

## 자산 상태와 주소

자산은 candidate → review → approved/rejected 상태를 갖는다. 파일 생성/업로드 성공이 승인이라는 뜻은 아니다. 위 상태는 콘텐츠 생애주기와 별개인 asset 객체 상태다.

Asset 레코드: `asset_id`, `revision`, `origin_type`(official/owned/generated), `source_ref`, `rights_status`, `entity_ids`, `fact_ids`, `local_path`, `public_url`, `mime_type`, `dimensions`, `sha256`, `alt`, `review_status`, `reviewer`, `reviewed_at`.

- 후보 이미지를 product=ALL로 전체 글에 자동 배포하지 않는다.
- 실제 파일이 없거나 생성이 실패하면 실패로 남긴다. 이전 파일로 대체할 때는 파일의 revision과 대체 이유를 기록하고 다시 검토한다.
- Writer는 초안에 `{{asset:NEED-ID}}`로 이미지 요구 위치를 표시한다. Renderer는 해당 Need ID의 binding에서 승인된 Asset ID/revision을 찾아 최종 출력한다. 미승인 자산은 자리 표시자 또는 검토용 미리보기로만 다루며 발행 완료로 처리하지 않는다. 원문 URL은 asset registry에 둔다.
- 발행용 URL은 외부 접근·이미지 MIME·선택된 revision 일치를 확인한다. `/static/...`, localhost, 인증 필요 주소를 공개 CDN 주소로 간주하지 않는다.
- 이미지 하단에 내부 ID·체감효과 박스·자동 설명 캡션을 붙이지 않는다. alt는 접근성을 위해 유지한다. 출처/라이선스상 필요한 표기는 생략하지 않는다.

필수 자산 부족은 AssetNeed를 미해결로 남겨 콘솔에 노출한다. 선택적 자산은 생략 가능하지만 이를 ‘삽입 완료’로 기록하지 않는다. 최종 Renderer는 승인된 binding만 사용하며 글에 없는 이미지를 추가하지 않는다.
