# 여러 제품의 추천과 보조 노드 배치

상태: 설계안 / 2026-10-07. 기존 r27 규칙을 기준으로 정리한 템플릿 기획 계약이다. 새 제안은 활성 정책 릴리스에 아직 반영하지 않았다.

## 기존 규칙으로 정해진 것

| 판단 | 근거 정책 |
|---|---|
| 설정·배치로 해결되면 구매를 강요하지 않는다 | RULE-READER-STYLE-V2N0033 |
| 비교 글은 같은 결정 질문의 비교군을 다룬다 | GUIDE-03-STRUCTURE-V2N0049, V2N0083 |
| 기본 구성 / 조건부 추가 / 다른 글의 대안을 구분한다 | GUIDE-03-STRUCTURE-V2N0081 |
| 역할이 다른 장비를 서로 대체하는 대안으로 나열하지 않는다 | GUIDE-03-STRUCTURE-V2N0065 |
| 추가 부속은 남는 문제·역할·근거와 연결한다 | RULE-READER-STYLE-V2N0059, V2N0061 |
| 구성품의 기능과 성능 인과를 추정하지 않는다 | RULE-COMPONENT-ROLE-V2N0004, V2N0009 |
| 플랫폼·모드·펌웨어·라이선스 조건을 보존한다 | RULE-PLATFORM-SCOPE-V2N0006 |
| 여러 제품을 설명하면 제품별 소개 링크를 둔다 | RULE-OCEANTECH-BRAND-LINKS-V2N0046, V2N0048 |

추천 제품은 한 개로 고정돼 있지 않다. 한 글의 중심 결정이 하나라는 규칙은 제품 수 제한이 아니다. 기존 AGENTS의 ‘글당 링크 1개’는 현재 브랜드 규칙보다 우선하지 않는다.

## 추가할 추천 설계 규칙

아래 ID는 신규 설계안 식별자다. 기존 정책을 대체하는 승인된 정책 ID가 아니다.

| 설계 ID | 규칙 | 적용 구성 요소 |
|---|---|---|
| REC-DESIGN-01 | 제품 수의 하한·상한을 고정하지 않는다. 각 제품이 같은 결정 질문에 기여하는 이유가 있어야 하며, 개수를 채우기 위해 후보를 추가하지 않는다. | body.comparison, body.configuration, body.extension, closing.next_action |
| REC-DESIGN-02 | 여러 제품은 **대안**, **함께 쓰는 구성**, **조건부 추가** 중 어떤 관계인지 묶음별로 명시한다. 같은 목록에서 관계가 다른 제품을 동급 추천으로 섞지 않는다. | body.comparison, body.configuration, body.extension |
| REC-DESIGN-03 | 대안은 동일한 질문·비교 기준으로 구분한다. 각 후보의 적합 조건과 선택 이유를 설명하며 모두 구매하라는 의미를 만들지 않는다. 근거가 없으면 ‘최고’, ‘무조건 추천’ 등의 순위를 붙이지 않는다. | body.comparison |
| REC-DESIGN-04 | 구성은 도입할 제품과 재사용할 장비, 각 역할을 구분한다. 함께 쓸 수 있다는 주장은 별도의 구성·호환 근거에 연결한다. | body.configuration |
| REC-DESIGN-05 | 조건부 추가는 먼저 기본 구성을 설명한 뒤, 남는 문제와 추가 조건을 붙인다. 필요하지 않은 독자가 기본 구성의 필수품으로 오해하지 않게 쓴다. | body.extension, closing.next_action |
| REC-DESIGN-06 | 제품별로 이름·역할·질문과의 관계·추천 이유·적합 조건·중요 제약·Fact/출처·등록 소개 링크를 연결한다. 근거가 부족하면 추천 완료로 표시하지 않는다. | body.definition, body.comparison, body.configuration, body.extension, closing.next_action |
| REC-DESIGN-07 | 제품 인지는 이름·역할·주제와의 관련성을 설명하는 선택이다. 인지만으로 구매 필요성이나 문제 해결 효과를 암시하지 않는다. 추천으로 변경하려면 추천 이유와 적합 조건을 추가 검증한다. | body.definition, body.explanation, closing.next_action |
| REC-DESIGN-08 | 본문 추천을 보조 노드에서 길게 반복하지 않는다. 본문에서 이미 설명했다면 간단히 회수하거나 생략한다. 새 제품은 그 위치에서 역할·추천 조건·근거를 설명한다. | body.explanation, body.extension, closing.next_action |

## 유형별 배치

보조 노드는 선택형이다. 모든 글에서 아래 요소를 강제로 추가하지 않는다.

| 글 유형 | 본문 추천 위치 | 보조 노드 두 배치 선택과 기본 제안 |
|---|---|---|
| 문제 해결 | 점검·설정으로 해결되는지 확인한 뒤, 장비의 한계가 확인된 경우에 추천 | **점검·조치 뒤** 제품 인지 / **다음 행동·상담**에서 제품 인지. 실제 도입 요구가 확인되면 추천으로 선택 변경 가능 |
| 기능 설명 | 기능의 동작·효과 범위·조건을 설명한 뒤 적용 제품을 연결 | **기능 설명 뒤** / **다음 행동·상담**. 적용 조건에 맞는 제품 또는 동일 질문의 대안 묶음 |
| 회의실 구성 | 요구와 기존 장비를 정한 뒤 기본 구성에 포함 | **구성 설명 뒤** 역할 보충 / **다음 행동·상담**에서 조건부 추가. 본문의 기본 구매 구성을 보조 노드로만 숨기지 않는다 |
| 제품 비교 | 기본 역할과 동일 비교 기준을 설명한 뒤 조건별 선택 결론 | **비교 결론 뒤** / **다음 행동·상담**. 비교한 제품 소개가 충분하면 보조 노드 생략 |
| 제품 소개 | 주제 제품의 정의·기능·적합 조건 설명에 포함 | 기본은 생략. 보완할 문제가 있으면 **제품 설명 뒤** / **다음 행동·상담**에 조건부 추가 |

마감 배치는 ‘답 회수·다음 행동 → 제품 보조 설명 → 상담·맺음 인사 → 문의 배너’다. 시작 인사 안이나 마지막 문의 배너 뒤에 넣지 않는다. 기존 `position` 값과 `anchor_section_id`를 사용한다.

## 기획 데이터와 작성 순서

`recommendation-plan.schema.json`을 별도 기획 계약으로 사용한다. 기존 Writer의 응답 필드는 변경하지 않는다.

1. 독자 질문과 중심 결정을 정한다.
2. 본문 추천과 보조 노드 선택을 구분한다. 선택 이유와 위치를 기록한다.
3. 제품 관계별 묶음과 제품별 역할·선택 조건을 작성한다.
4. 제품 주장과 Fact ID·출처를 연결한다. 구성 묶음은 호환 근거도 연결한다.
5. 제품 소개 URL은 제품 레지스트리에서 조회한다. 근거·링크가 미확정이면 pending/blocked와 미해결 이유를 남긴다.
6. Writer는 검증된 제품별 정보만 자연어로 풀어 쓴다. QA는 선택 조건 누락, 역할 혼동, 인지의 구매 권유 변질, 추천 중복을 확인한다.

`ready`는 필수 정보가 연결됐다는 상태이며, Fact의 정확성과 호환성은 별도로 검토해야 한다. 각 묶음의 제품 수는 제한하지 않되, 대안 묶음은 비교가 가능하도록 두 후보 이상으로 구성한다. 준비되지 않은 대안은 pending 상태로 남길 수 있다.

제품 인지의 `reason`은 주제와의 관련성을 뜻한다. 추천용 이유로 해석하지 않는다. 같은 제품이 한 묶음에 중복되지 않는지, `base_group_id`가 실제 기본 구성 묶음을 가리키는지, 보조 노드 선택의 `product_ids`와 계획이 일치하는지도 QA에서 확인한다. 스키마만으로 이 관계와 자연어 근거의 정확성을 판정하지 않는다.

새 제안 8개는 `recommendation-design-rules.json`에 draft·비활성 상태로 저장했다. 기존 규칙 조회 ID는 `recommendation-policy-baseline.json`에 기록했다. 이 파일들은 운영 workspace와 별도로 보관하는 설계 자료다.

## 구현 범위

글 작성·수정·발행 후 추천 이력과 제품별 빈도는 [제품 추천 기록·검증·빈도 관리 가이드](../../rules/product-recommendation-tracking.md)에 따라 관리한다. 본문·보조 노드·링크 반복은 같은 글의 추천 횟수를 늘리지 않는다. 기획 시 이전 추천 질문·조건·조합을 참고한다.

이번 변경은 추천 가이드와 기획 스키마, 보조 노드 설계 참조를 추가한다. 운영 Planner·Writer·QA가 기획 계약을 소비하고 저장하는 연결은 아직 구현하지 않았다. 실제 제품 선정과 20개 주제별 Fact 검증은 이 계약에 따라 후속 수행한다.
