## 1. 목표와 완료의 의미

기존 자연어 정책을 **독립적으로 이해·판정·개정할 수 있는 의미 단위**로 만들고, 여러 관점으로 묶어 읽으며 관계와 변경 영향을 추적할 수 있게 한다.

문장을 짧게 나누거나 키워드를 붙이는 것만으로 완료하지 않는다. 다음 질문에 답할 수 있어야 한다.

1. 이 규칙은 누가 어떤 대상에 어떤 조건에서 무엇을 하라는 것인가?
2. 어떤 작업·글 요소·주제에 적용되는가?
3. 어떤 규칙을 함께 읽어야 하고, 어떤 예외·금지·권한 경계가 있는가?
4. 현재 유효한 정책인가, 미승인 설계인가, 참고 예문인가?
5. 원문이 바뀌면 어떤 정책·그룹·관계·실행 입력을 다시 검토해야 하는가?
6. AI가 한 주제를 조회해 관련 규칙을 빠짐없이 이해할 수 있는가?

정책 분해는 기존 의미의 표현 방식 변경이다. 정책의 신설·폐지·우선순위 변경과 구분한다. 현재 요청은 가이드 전달이며, 이 문서 자체가 실행·활성화 권한을 부여하지 않는다. 후속 AI는 실제 받은 사용자 요청의 범위를 확인한다.

## 3. 실행 순서

### A. 인벤토리와 기준선

- 등록 가이드·규칙·프롬프트·최근 설계 문서를 목록화한다.
- 각 문서의 경로·해시·버전·상태·등록 여부·활성 릴리스 포함 여부를 기록한다.
- 원문 블록 ↔ 현재 atom ↔ 조립 위치의 연결을 확인한다.
- archive와 과거 releases는 이력·대조 자료로 취급한다. 현재 규칙으로 중복 수입하지 않는다.
- 등록되지 않은 최근 설계는 draft로 목록에 포함한다. 활성 정책으로 간주하지 않는다.
- 조립 결과와 현재 검색 결과를 기준선으로 저장한다. 작업 전후 차이를 비교할 수 있어야 한다.

### B. 한 묶음으로 방식 검증

제품 추천을 첫 표본으로 삼는다. 관련 정책을 키워드뿐 아니라 원문 문맥으로 모두 찾아 사람이 검토 가능한 목록을 만든다. 이 묶음에서 의미 분해·관계·조회·업데이트까지 끝까지 검증한 뒤 전체로 확장한다.

표본 범위에는 구매 강요 금지, 기본 구성, 대안, 조건부 추가, 역할·호환, 제품 인지, 제품 소개 링크, 배치, 근거·과장이 포함된다. ‘추천’이라는 단어가 없는 정책도 찾는다.

### C. 전체 의미 검토

브랜드 → 기획·문체·배치 → 제품·Fact·주의사항 → 자산 → 집필 출력 → 검토·승인 → 발행·운영 순으로 검토한다. 이것은 작업 편의를 위한 순서이며 정책 권한 순위가 아니다.

한 묶음마다 추출·분류·관계·미해결 항목을 저장한다. 모든 묶음 완료 후 분야 사이의 누락·중복·충돌을 다시 검토한다. 중간 저장은 하되 미검토 항목을 완료로 바꾸지 않는다.

## 4. 의미 단위 분해 규칙

**다르게 개정되거나 예외를 가질 수 있는 지시라면 분리한다.** 한 문장인지 여러 문장인지로 결정하지 않는다.

- 의무·금지·허용·권고는 구분한다. ‘가능하다’를 반드시 하라는 의미로 바꾸지 않는다.
- 조건절과 제한 범위는 규칙에 붙인다. ‘필요한 경우’, ‘호환되는 장비에서’, ‘실제 기록이 있을 때만’을 삭제하지 않는다.
- ‘이 제품’, ‘그 경우’, ‘위 규칙’은 문맥을 찾아 대상을 명시한다. 불명확하면 검토 대기다.
- 역할이 다른 대상·행동이 한 문장에 있으면 분리한다. 한 행동의 목적 설명은 함께 보존할 수 있다.
- 숫자·제품 성능·호환 목록은 정책 자체와 Fact를 구분한다. 제품 사실을 새 정책 사실로 복제하지 않는다.
- 제목·버전·예문·표·코드가 항상 비규범인 것은 아니다. 실제 계약을 정의하는 표·코드인지 문맥으로 판단한다.
- 예문의 문체·제품·수치는 자동 의무나 검증된 Fact로 승격하지 않는다.
- 원문 인용과 정규화된 정책 문장을 별도로 보존한다. 정규화에 새 요구를 추가하지 않는다.

예: “추가 장비는 남는 문제가 있을 때 설명하고 실제 사진과 제품 소개 링크를 계획한다.”

- 조건부 추가의 제시 조건: 남는 문제가 있을 때.
- 설명 내용: 추가 장비의 문제 보완 역할.
- 자산 계획: 해당 장비의 실제 사진.
- 링크 계획: 해당 제품의 등록 소개 URL.

네 지시가 서로 다른 시점·대상에 적용된다면 분리하고 공통 조건과 `requires_context` 관계로 다시 연결한다. 연결을 잃는 분할은 금지한다.

## 5. 원자 데이터 계약

기존 스키마와 저장 서비스의 호환성을 확인한 후 확장한다. 아래는 필요한 개념이며 기존 필드를 무조건 이름 변경하라는 지시가 아니다.

| 영역 | 필요한 정보 |
|---|---|
| 식별 | 영구 ID, revision, 상태, 제목, 원문, 정규화 문장 |
| 의미 | 주체, 행동, 대상, 규범, 조건, 예외, 목적 |
| 적용 | 실행 단계, 글 요소, 글 유형, 분야, 용도, 주제 태그 |
| 권한 | 수준, 정한 주체, 위임·승인 근거, 허용된 예외 범위 |
| 출처 | 문서 ID·revision·경로·행 범위·인용·해시·원문 슬롯 |
| 변경 | supersedes/derived_from, 유효 기간, 변경 요청·이유 |
| 검토 | 의미 검토 상태, 근거, 검토자, 검토 시각, 미해결 질문 |
| 판정 | 검증 방식, 적용되는 검사기, 실패 처리 |

‘모두 적용’과 ‘미분류’를 구분한다. 해당 없음과 미확인을 구분한다. 의미 필드를 채울 근거가 없으면 unknown/needs_review와 구체적인 질문을 저장한다. 필드를 채우기 위해 권한자·조건·예외를 창작하지 않는다.

ID는 제목·정렬·행 번호가 바뀌어도 안정적으로 유지한다. 재분할 시 기존 ID를 제거하지 말고 부모/자식·폐기·대체 이력을 남긴다. 동일 정책의 문구 수정과 새로운 정책으로 분리하는 변경은 구분한다.

## 6. 분류와 관계

### 분류 축

주제·분야·단계·용도·글 구성 요소·글 유형·규범·권한·출처는 별도 축이다. 복수 적용을 허용하되 선택 이유를 기록한다. 태그의 표준 ID·정의·별칭을 관리한다. 문자열 유사도는 후보 발견에만 사용한다.

제품 추천의 하위 관점: alternatives(대안), bundle(조합), awareness(제품 인지), fit_conditions(적합 조건), compatibility(호환), evidence(근거), product_links(소개 링크), placement(배치).

제품 인지와 추천은 별도 역할이다. 대안과 조합은 제품들 사이의 관계다. 배치 위치는 본문 연결 정보다. 이들을 하나의 태그로 뭉개지 않는다.

### 관계 종류

- `requires_context`: 함께 읽어야 의미가 유지되는 전제.
- `depends_on`: 적용·실행의 선행 요구.
- `complements`: 서로 보완하지만 같은 규칙은 아님.
- `exception_to`: 명시적으로 허용된 예외와 그 조건.
- `conflicts_with`: 적용 조건이 겹칠 때 동시에 만족할 수 없음.
- `overlaps_with`: 일부 범위가 겹침.
- `duplicate_of`: 같은 의미·범위의 중복 후보.
- `supersedes`: 개정 관계.

관계에는 근거·방향·적용 조건·검토 상태를 저장한다. 정책 그래프와 제품 호환 그래프를 섞지 않는다. 예외·개정 순환, 존재하지 않는 대상 ID 등을 검사한다. 같은 주제라는 이유만으로 모든 정책끼리 연결하지 않는다.

## 7. 충돌 검토

같은 대상·행동에서 적용 조건이 실제로 겹치는지 확인한다. 금지/의무뿐 아니라 수량·순서·출력 계약·승인 조건 차이도 검토한다.

예: ‘제품 링크 하나만’과 ‘설명한 제품별 링크’는 적용 범위·활성 버전·개정 관계를 확인해야 한다. 과거 릴리스 규칙을 현재 규칙과 섞어 충돌로 보고하지 않는다.

권한과 Fact 증거력은 구분한다. 최신 문서가 항상 이기는 방식으로 해결하지 않는다. 기존 위계 설계를 참고하되 현재 데이터에 수준이 붙어 있다는 이유만으로 변경·예외 권한이 구현됐다고 주장하지 않는다.

충돌 후보는 근거와 해결안을 기록한다. 원문 뜻을 바꾸는 결정은 별도 변경 요청으로 남긴다. 애매한 항목 하나 때문에 모든 추출을 중단하지 말고 확실한 범위는 계속 검토한다.

## 8. AI용 조회 결과

‘제품 추천 정책’ 같은 주제 조회는 다음을 반환한다.

1. 직접 관련 정책: 현재 적용되는 의무·금지·허용·권고.
2. 필요한 공통 제약: 근거·호환·링크·과장 등 연결 관계로 확장된 정책.
3. 조건·예외·충돌 후보·미해결 항목.
4. 포함 이유, source 위치·인용, revision·검토 상태.
5. 검색 범위·제외한 archive/draft·확인하지 못한 영역.

한 규칙을 여러 묶음에서 찾더라도 원자 자체는 중복 저장하지 않는다. 모든 전역 규칙을 매번 쏟아 넣지 말고 관련성·의존 관계와 적용 조건을 설명한다. 오래된 collections는 사용하지 않는다.

별칭·태그·구조 조회를 우선하고 필요하면 의미 검색을 보조로 사용한다. 임베딩 유사도만으로 완전한 조회를 보장하지 않는다. 현재 규모에서는 별도 검색 서버보다 의미 데이터의 품질이 우선이다.

## 9. 업데이트와 운영 연결

- 원문 변경 감지 → 영향을 받는 원자 식별 → 의미·분류·관계 검토 → 파생 그룹 갱신 → 조회·조립 검증 순서로 처리한다.
- 그룹과 인덱스에 원본 workspace revision·스키마 버전을 기록한다. 어긋나면 재생성하거나 명시적으로 차단한다.
- 의미가 바뀌지 않은 재배치와 규범 변경을 구분한다. 이전 원자·승인·릴리스 기록은 보존한다.
- 활성 릴리스와 작업 중인 기획·편집본을 분리한다. 실행 중인 run의 고정된 입력을 바꾸지 않는다.
- 조회 UI만 개선했는지, 실행 AI 입력 선택까지 연결했는지 구체적으로 보고한다.
- 실제 자동 판정기가 없는 정책을 deterministic 검사 완료로 표시하지 않는다.

## 10. 검증과 완료 기준

### 내용 보존

모든 입력 규범이 atom 또는 설명된 미해결 상태로 추적되는가? 분해 전후 조건·예외·목적·의무 강도가 유지되는가? 원문 ↔ atom ↔ 읽기용 가이드 연결이 있는가?

가능하면 조립 본문의 동일성을 확인한다. 문구 정규화로 바뀌는 경우 원문과 의미 차이 검토표를 제공한다. 해시 일치만으로 의미 검토를 대신하지 않는다.

### 구조·변경 검증

ID·관계·조건·출처 유효성, retired 항목 제외, revision 동기화, 원문 변경 시 검토 무효화, 사용자 편집 손실 방지를 검사한다. 실제 스키마·저장·조립 변경에 맞는 테스트를 작성한다. 단순 출력 존재만 검사하는 테스트로 끝내지 않는다.

### 조회 검증

제품 추천, 이미지 자산, 인사말, 사실 근거, 공식 검토 등 여러 관점에서 사람이 검토한 기준 목록과 조회 결과를 대조한다. 기준 목록의 완전성을 검토하고 누락·과잉 포함을 기록한다. 표본 결과를 전체 정확도로 일반화하지 않는다.

### AI 탐색 체감 검증

실제 시작/종료 시각, 조회 횟수, 원문 추가 탐색 횟수, 사용한 입력 규모, 누락·모호성, 답변의 근거 추적 가능성을 기록한다. 파일 검색 밀리초와 AI가 이해하는 시간을 구분한다. 역할·검토 문맥을 밝히고 같은 AI가 만든 기준 목록만으로 독립 검증 완료를 주장하지 않는다.

### 완료 상태

각 묶음은 extracted → semantically_reviewed → relations_reviewed → retrieval_verified처럼 구분한다. pending/blocked와 이유를 남긴다. AI 검토와 사람의 승인도 구분한다. 의미 필드가 채워졌다는 이유만으로 검토 완료로 올리지 않는다.

## 11. 산출물과 최종 보고

필수 산출물: 입력 인벤토리, 스키마·마이그레이션, 원자 및 다축 분류, 관계 목록, 조회 가능한 묶음, 미해결·충돌·변경 영향 목록, 검증·AI 탐색 기록, 유지보수 설명.

현재 저장 서비스·UI·실행 코드와 호환되게 구현한다. 직접 workspace JSON을 덮어써 동시 편집·revision·history를 우회하지 않는다. 기존 API/잠금/commit 경로를 쓰거나 안전한 migration을 먼저 구현한다. 새 필드가 저장 시 유실되지 않는지 확인한다.

최종 보고에는 완료한 범위, 미완성 항목, 의미 변경 여부, 조회 전후 누락 사례, 실제 AI 탐색 시간, 활성화 여부, 재현 방법을 포함한다. 작업이 오래 걸린다는 이유로 근거 없는 시간 견적이나 품질 보장을 반복하지 않는다.

## 12. 다른 AI에게 보낼 시작 요청

> `content-system/00_system/policy/QUARKIZATION-WORK-GUIDE.md`와 연결된 TODO·감사·위계 설계를 읽고, 현재 정책 구조를 확인해 쿼크나이제이션을 진행해 주세요. 먼저 제품 추천 묶음에서 의미 분해·다축 분류·관계·조회·업데이트 처리를 끝까지 검증한 뒤 기존 등록 가이드 전체로 확장하세요. 기존 정책 뜻과 출처·이력을 보존하고, 불명확한 항목은 질문과 상태를 기록하세요. 문자열 분리나 키워드 자동 분류를 완료된 의미 분석으로 보고하지 마세요. 실제 AI 탐색 시간·조회 횟수·원문 재탐색·누락을 검증하고, 설계·편집본·활성 실행 정책을 구분해 보고하세요. 활성 릴리스 변경은 이번 요청 범위에 포함하지 않습니다.

위 시작 요청의 실행 범위는 전달하는 사용자가 조정할 수 있다. 이 문서를 읽은 사실만으로 별도 AI 생성·외부 메시지·정책 승인 권한이 생기는 것은 아니다.
